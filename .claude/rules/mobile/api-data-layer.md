# Mobile API & Data Layer Rule (oRPC + TanStack Query on native)

> Read on demand before touching the data layer in `apps/mobile/`. Overrides the
> web `@.claude/rules/api.md` for this app: `@` maps to `./` (no `src/`),
> translations come from `react-i18next` (not `next-intl`), the API client goes
> through the **Next.js `/api/dax` proxy** (so the backend host is never shipped),
> not the backend directly, and tokens live in Expo **SecureStore**
> (not `localStorage`). The oRPC + TanStack Query contract rules from
> `.claude/rules/api.md` and `.claude/rules/state/tanstack-query.md` still apply —
> this file only restates the native-specific divergences.

The mobile app talks to the same DAX admin backend through the same **oRPC**
contract as the web admin app, surfaced as typed TanStack Query utilities. Follow
these patterns — do not invent new clients or hand-roll fetches.

---

## 1. The contract is the source of truth

- All API types and the router come from `@repo/api` (the same package the web app
  uses). The mobile client is built in `apps/mobile/lib/api/client.ts` from
  `adminContract` + `OpenAPILink` + `createORPCClient`, exactly like
  `apps/admin/src/lib/api/client.ts`.
- **NEVER hand-write request/response types.** Import them from `@repo/api`, or
  derive with `Awaited<ReturnType<typeof tripsClient.getInOrg>>`. This is
  `core/typescript-strict.md` §3.
- If a type is missing, add it to the contract package — never redeclare it locally.

---

## 2. One typed client — `apiContracts` + named clients

`apps/mobile/lib/api/client.ts` exports a single TanStack Query entry point
(`apiContracts`) and the named clients (`authClient`, `tripsClient`,
`driversClient`, `vehiclesClient`, `routesClient`, `usersClient`,
`socialClient`, …), all built from one `adminClient`.

- **Queries** — `apiContracts.<namespace>.<procedure>.queryOptions({ input })`
- **Mutations** — `apiContracts.<namespace>.<procedure>.mutationOptions({ … })`
- **Invalidation key** — `apiContracts.<namespace>.<procedure>.key()`
- **Imperative one-off calls** (inside a `mutationFn`, an event handler that isn't
  a mutation) — the named client (`tripsClient.getInOrg({ id })`).

```tsx
// ✅ Correct — query key + fetcher generated by the contract, called inline
import { useQuery } from "@tanstack/react-query";
import { apiContracts } from "@/lib/api/client";

const { data, isLoading, isError } = useQuery(
  apiContracts.trips.getInOrg.queryOptions({ input: { id: tripId } }),
);
```

```tsx
// ❌ Wrong — hand-written queryKey + queryFn + a raw fetch
const { data } = useQuery({
  queryKey: ["trips", tripId],
  queryFn: () => fetch(`${API}/trips/${tripId}`).then((r) => r.json()),
});
```

**NEVER wrap a single query/mutation in a custom hook** (no `useTripSearch`,
`useSeatMap` that only forwards one call). Call `useQuery` / `useMutation` inline
with the contract helper. A hook is justified only when it adds real shared logic
(debounce + derived state + a query, reused in 2+ screens) — see
`react/hooks-rules.md`.

---

## 3. skipToken — not `enabled: false`

Make a query conditional by passing `skipToken` as the `input`. Type-safe: the
fetcher is never called and `data` is correctly typed as possibly `undefined`.

```tsx
// ✅ Correct
import { skipToken } from "@tanstack/react-query";

useQuery(
  apiContracts.trips.getInOrg.queryOptions({
    input: tripId ? { id: tripId } : skipToken,
  }),
);

// ❌ Wrong — never fake the input with `!` to satisfy types
useQuery(
  apiContracts.trips.getInOrg.queryOptions({
    input: { id: tripId! },
    enabled: !!tripId,
  }),
);
```

## 4. Cache invalidation — use generated keys

Build invalidation keys from the contract helpers (partial match), never
hand-rolled arrays — manual `["trips"]` keys will **not** match contract keys.

```tsx
const queryClient = useQueryClient();

const inviteDriver = useMutation(
  apiContracts.drivers.invite.mutationOptions({
    onSuccess: () => {
      void queryClient.invalidateQueries({
        queryKey: apiContracts.drivers.list.key(),
      });
    },
    onError: (error) => toast.error(resolveApiError(error)),
  }),
);
```

`.key()` is a partial-match key (good for invalidation). Use `.queryKey({ input })`
only when you need the exact key (e.g. `setQueryData`).

---

## 5. Always handle all states

Every query consumer handles loading / error / empty.

```tsx
if (isLoading) return <Spinner />;
if (isError) return <ErrorState message={resolveApiError(error)} />;
if (!data?.items.length) return <EmptyState />;

return <TripList items={data.items} />;
```

## 6. Base URL — one source, through the `/api/dax` proxy

The mobile app talks to the Next.js **`/api/dax` proxy** served by the admin web
app — **not** the backend directly. The proxy
(`apps/admin/src/app/api/dax/[...path]/route.ts`) forwards to the real
`DAX_API_URL`, which lives only on the server, so the backend host
(`dev-api.daxsystem.md`) is never shipped in the mobile bundle or visible in
network traces — clients only ever see the proxy origin (`dev.daxsystem.md`). This
mirrors the web client, which uses `${window.location.origin}/api/dax`.

The base URL resolves from **one** module — `apps/mobile/lib/api/base-url.ts`:

```ts
// apps/mobile/lib/api/base-url.ts — the single source of truth
const DEFAULT_PROXY_URL = "https://dev.daxsystem.md/api/dax";

export const DAX_API_BASE_URL = (
  process.env.EXPO_PUBLIC_DAX_API_URL ?? DEFAULT_PROXY_URL
).replace(/\/$/, "");
```

- MUST resolve the base URL from `lib/api/base-url.ts`. Both `client.ts` and
  `fetch-with-auth.ts` import `DAX_API_BASE_URL` from it.
- **NEVER read `process.env.EXPO_PUBLIC_DAX_API_URL` directly** elsewhere, and
  **NEVER hardcode the backend host** (`dev-api.daxsystem.md`) anywhere in
  `apps/mobile` — only the proxy origin (`dev.daxsystem.md`) may appear.
- Override per environment with `EXPO_PUBLIC_DAX_API_URL` (e.g. a local admin at
  `http://localhost:3000/api/dax`; use the LAN IP, not `localhost`, on a physical
  device).
- The proxy keeps the app's `Authorization: Bearer` header (no admin session
  cookie is present), so native Bearer auth works through it; the app still does
  its own refresh-on-401 (`fetch-with-auth.ts`).

```ts
// ❌ Wrong — bypasses the proxy, ships the backend host, divergent fallbacks
// client.ts:           process.env.EXPO_PUBLIC_DAX_API_URL ?? "https://dev-api.daxsystem.md"
// fetch-with-auth.ts:  process.env.EXPO_PUBLIC_DAX_API_URL ?? ""
```

> Only `EXPO_PUBLIC_*` vars are inlined into the native bundle by Expo — server-only
> secrets have no place here (mirrors `core/env.md` §4: if the device needs it, it
> isn't a secret). The real `DAX_API_URL` stays a **server-only** var on the admin
> deployment.

## 7. `x-locale` header from `react-i18next`

The mobile client is a module singleton outside React, so it cannot call a hook for
the locale — mirror the web `getApiLocale()` pattern in
`apps/admin/src/lib/api/locale.ts`, but source the locale from `react-i18next`.

- MUST send `x-locale` via the link's `headers` callback (evaluated per request),
  reading `i18n.language` from `apps/mobile/i18n/index.ts`.
- The `headers` callback on `OpenAPILink` is the same mechanism the web client uses
  (`apps/admin/src/lib/api/client.ts` → `headers: () => ({ "x-locale": getApiLocale() })`).

```ts
// ✅ Correct — apps/mobile/lib/api/client.ts
import i18n from "@/i18n";

import { DAX_API_BASE_URL } from "./base-url";

const adminApiLink = new OpenAPILink(adminContract, {
  url: DAX_API_BASE_URL,
  headers: () => ({ "x-locale": i18n.language }),
  fetch: authFetch,
});

// ❌ Wrong — locale captured once at module load, never updates on language change
const locale = i18n.language;
const link = new OpenAPILink(adminContract, {
  headers: { "x-locale": locale },
});
```

## 8. Token refresh — typed contract, refresh token in the body

The current `apps/mobile/lib/auth/fetch-with-auth.ts` refreshes by hand-rolling a
raw `globalThis.fetch` to `/auth/refresh`, sending the refresh token in the
**`Authorization` header**, and reading `data.accessToken` / `data.refreshToken`
off an **untyped** `res.json()`. That is wrong on three counts.

Compare the web admin server path, which is the correct shape:
`serverAuthClient.refresh({ refreshToken })` (typed contract,
`refreshToken` in the request **body**, typed result) —
`apps/admin/src/lib/auth/server-refresh.ts`.

Requirements for the native refresh:

- MUST refresh through the typed contract — `authClient.refresh({ refreshToken })`,
  with the refresh token **in the body**, through a **bare unauthenticated link**
  (a second oRPC link with no auth `fetch`, so the refresh call itself never
  attaches the dead access token and never re-enters the refresh path).
- MUST keep a **single in-flight refresh promise** (the existing `refreshPromise`
  guard in `fetch-with-auth.ts` is correct — preserve it) so concurrent 401s share
  one refresh.
- MUST exclude auth paths from the 401-retry (the existing `url.includes("/auth/")`
  guard is correct — preserve it) to avoid refresh loops.
- On refresh failure, clear tokens via `tokenStore.clearTokens()`
  (`apps/mobile/lib/auth/secure-store.ts`) and return the original `401`.
- **NEVER** put the refresh token in the `Authorization` header.
- **NEVER** hand-roll the response shape — let the contract type
  `{ accessToken, refreshToken }`.

```ts
// ❌ Wrong — today's apps/mobile/lib/auth/fetch-with-auth.ts
const res = await globalThis.fetch(`${DAX_API_URL}/auth/refresh`, {
  method: "POST",
  headers: { Authorization: `Bearer ${refreshToken}` }, // wrong: token in header
});
const data = await res.json();                          // wrong: untyped shape
await tokenStore.setTokens(data.accessToken, data.refreshToken);
```

```ts
// ✅ Correct (planned) — typed contract via a bare, unauthenticated link
import { bareAuthClient } from "@/lib/api/client"; // link without authFetch

async function refreshTokens(): Promise<boolean> {
  try {
    const refreshToken = await tokenStore.getRefreshToken();
    if (!refreshToken) return false;

    const { accessToken, refreshToken: next } =
      await bareAuthClient.refresh({ refreshToken }); // token in body, typed result
    await tokenStore.setTokens(accessToken, next);
    return true;
  } catch {
    return false;
  }
}
```

Token storage stays in `apps/mobile/lib/auth/secure-store.ts` (Expo `SecureStore`
on device, `localStorage` only on the web target) — never read or write the
`Authorization`/refresh tokens anywhere else.

## 9. Errors — map `ORPCError` to localized messages

oRPC failures throw `ORPCError`. Map them to user-facing, localized strings — never
collapse every failure to one generic key.

- MUST resolve messages via `apps/mobile/lib/api/errors.ts` (planned), mirroring
  the web `apps/admin/src/lib/api/errors.ts` (`isORPCError` guard + the
  `@repo/api` error catalogs + `resolveMessage` keyed by the active locale).
- The active locale comes from `i18n.language` (`react-i18next`), the same source
  as the `x-locale` header (§7).

```ts
// ✅ Correct (planned) — apps/mobile/lib/api/errors.ts
import { isORPCError, resolveMessage } from "@repo/api";
import i18n from "@/i18n";

export function resolveApiError(error: unknown): string {
  if (isORPCError(error)) {
    return resolveMessage(error.code, i18n.language) ?? i18n.t("errors.generic");
  }
  return i18n.t("errors.generic");
}
```

```tsx
// ❌ Wrong — every error collapses to one key, ORPCError codes discarded
onError: () => toast.error(t("errors.generic"));
```

## 10. Pre-change checklist

Before touching the mobile data layer, confirm in order:

1. Does the call go through `apiContracts` / a named client from
   `apps/mobile/lib/api/client.ts`? (No raw `fetch`, no hand-written `queryKey`.)
2. Is a conditional query using `skipToken`, not `enabled: false` + `!`?
3. Is invalidation built from `.key()`, not a literal array?
4. Is the base URL read from the single validated env module (§6), not
   `process.env` directly?
5. Is `x-locale` sent via the link `headers` callback from `i18n.language` (§7)?
6. Does refresh go through the typed contract, token in the body, single in-flight
   promise, auth paths excluded (§8)?
7. Are errors resolved through `lib/api/errors.ts`, not collapsed to one key (§9)?
