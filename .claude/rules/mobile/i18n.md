# i18n Rule — Internationalization in `apps/mobile`

> Read on demand for `apps/mobile`. Overrides the web rule `.claude/rules/i18n/next-intl.md` for this app — there is no `src/` so `@/*` maps to `./*`, copy is consumed through **react-i18next** (`useTranslation`) not **next-intl**, there is no locale URL segment (the device/stored locale drives `i18n.language`), and the persisted choice lives in **expo-secure-store** not `localStorage` while the API client talks to the **direct** `EXPO_PUBLIC_DAX_API_URL` (no Next.js proxy).

The mobile app shares its translation catalogs with admin through `@repo/i18n`, but
reads them with the `i18next` runtime instead of next-intl. Follow these patterns —
do not reach for next-intl APIs, and do not re-implement locale plumbing per file.

---

## 1. Use react-i18next — NEVER next-intl

next-intl is web-only. On native, ALWAYS read copy through `useTranslation` from
`react-i18next`. The shared `i18next` instance is created in
`apps/mobile/i18n/index.ts` and provided by `I18nProvider`
(`apps/mobile/providers/i18n-provider.tsx`, mounted in `apps/mobile/app/_layout.tsx`).

```tsx
// ✅ Correct — react-i18next, namespace-scoped
import { useTranslation } from "react-i18next";

export function BookNowButton() {
  const { t } = useTranslation("common");
  return <Button>{t("bookNow")}</Button>;
}

// ❌ Wrong — next-intl does not exist on native (no router/locale segment)
import { useTranslations } from "next-intl";
const t = useTranslations("content.common");
```

- Copy comes from `@repo/i18n` shared catalogs (`packages/i18n/locales/<locale>/<ns>.json`),
  the SAME JSON admin renders with next-intl. NEVER fork or inline native-only strings.
- There is no `getTranslations`/server-component split on native — every component is a
  client component, so `useTranslation` is the only entry point.
- To read/switch the active language outside a component, import the singleton:
  `import i18n from "@/i18n"` and use `i18n.t(...)` / `i18n.changeLanguage(...)`.

---

## 2. Register EVERY bundled namespace in `buildI18nextResources`

The `resources` passed to `i18next.init` come from `buildI18nextResources()` in
`packages/i18n/src/i18next-resources.ts`. A namespace that is bundled but **not**
listed there is invisible to `i18next` — `t("offer:title")` will echo the key
(`"offer:title"`) instead of the translation, with no error.

```ts
// packages/i18n/src/i18next-resources.ts — every bundled ns MUST be assigned
r.common = b.common as Record<string, unknown>;
r.errors = b.errors as Record<string, unknown>;
// ...
r["buy-tickets"] = b["buy-tickets"] as Record<string, unknown>;
```

- The catalog `offer` IS bundled (`packages/i18n/src/bundled-locale-json.ts` imports
  `enOffer`/`roOffer`/`ruOffer`) but is currently **missing** from
  `buildI18nextResources()`. Add `r.offer = b.offer as Record<string, unknown>;`
  before relying on the `offer` namespace on native (planned). Until then, the offer
  flow will render raw keys.
- When you add a NEW namespace JSON to `@repo/i18n`, you MUST: (1) import it in
  `bundled-locale-json.ts` for all three locales, (2) add it to `NextIntlMessages`
  and each locale object, and (3) assign it in `buildI18nextResources()`. Skipping
  step 3 breaks only native, silently.
- `defaultNS` is `"common"`, so bare keys (`t("bookNow")`) resolve against `common`.
  For any other namespace, pass it explicitly: `useTranslation("trips")` or
  `t("trips:list.title")`.

## 3. Persist the locale and hydrate in the correct order

The chosen locale MUST survive app restarts and reflect the signed-in user. Resolve
the startup language with this precedence (highest first):

| Priority | Source | Where |
|---|---|---|
| 1 | Backend preference | `me().preferences.locale` (`stores/auth.ts` → `authClient.me()`) |
| 2 | Stored choice | `expo-secure-store` (planned — see below) |
| 3 | Device default | `expo-localization` `getLocales()[0]?.languageCode` |

```ts
// apps/mobile/i18n/index.ts — current device-only detection
function detectLocale(): SupportedLocale {
  const device = getLocales()[0]?.languageCode ?? DEFAULT_LOCALE;
  return SUPPORTED_LOCALES.includes(device as SupportedLocale)
    ? (device as SupportedLocale)
    : DEFAULT_LOCALE;
}
```

- `detectLocale()` today covers **only** priority 3. Persistence (priority 2) and
  backend hydration (priority 1) are **planned** and MUST layer ON TOP — never replace
  device detection, which stays the final fallback when nothing is stored.
- Persist through the SecureStore wrapper pattern in `apps/mobile/lib/auth/secure-store.ts`
  (NEVER touch `expo-secure-store` directly from a component, and NEVER use
  `localStorage` — that branch exists only for the web target inside that wrapper).
- Switching the language MUST do all three: call `i18n.changeLanguage(locale)`,
  persist to SecureStore, and push to the backend (`userPreferences`). Today
  `apps/mobile/components/layout/language-switcher.tsx` only calls
  `i18n.changeLanguage` — wiring the persist + backend push is planned.

```tsx
// language-switcher.tsx — current behavior (persist + sync still planned)
function select(locale: SupportedLocale) {
  void i18n.changeLanguage(locale);
  setOpen(false);
}
```

### Backend sync (`userPreferences`)

- The contract (`@daxsystem/admin-api-contract` ≥ 0.5.8) exposes
  `apiContracts.userPreferences.*`; `me().preferences.locale` is a nullable enum.
  Mirror the admin provider `apps/admin/src/providers/user-preferences-sync.tsx`:
  hydrate from the backend on auth, then push a **debounced minimal PATCH** when the
  user changes language. A native `UserPreferencesSync` provider is **planned** — do
  not duplicate the debounce logic ad hoc.
- Backend is the source of truth on launch; the stored/device locale only seeds the
  first paint before `me()` resolves.

## 4. Send `x-locale` and localize API errors

The backend localizes responses (including error messages) from the `x-locale`
request header. The mobile API client MUST send it from `i18n.language`.

```ts
// apps/mobile/lib/api/client.ts — planned: add x-locale, mirroring admin
import i18n from "@/i18n";
import { normalizeLocale } from "@/i18n/normalize-locale"; // §5 (planned)

const adminApiLink = new OpenAPILink(adminContract, {
  url: DAX_API_URL,
  fetch: authFetch,
  headers: () => ({ "x-locale": normalizeLocale(i18n.language) }),
});
```

- Cross-ref `.claude/rules/api.md`: the OpenAPI/oRPC client is the single API entry
  point; the `x-locale` header is the only place locale crosses into the backend.
  Admin already does this (`apps/admin/src/lib/api/client.ts` →
  `headers: () => ({ "x-locale": getApiLocale() })`). Mobile reads `i18n.language`
  directly — there is **no** URL segment to parse like the web `getApiLocale()`, so
  do NOT port `lib/api/locale.ts`; resolve from `i18n.language` instead.
- The current `apps/mobile/lib/api/client.ts` sends **no** `x-locale` header (planned).
- Surface backend errors through the `errors` namespace
  (`useTranslation("errors")`). The `errors` catalog is already registered in
  `buildI18nextResources()`; map `ORPCError` codes to keys (a native error helper in
  `apps/mobile/lib/api/` is planned — mirror admin's `@/lib/api/errors`). NEVER show a
  raw backend string or swallow the error (see `core/coding-style.md` §4).

## 5. One shared `normalizeLocale` helper — NEVER duplicate split guards

`i18n.language` can be a region-tagged tag (`"en-GB"`, `"ru-RU"`) while
`SUPPORTED_LOCALES` are bare (`"en" | "ro" | "ru"`). The base-language extraction
MUST live in ONE helper and be reused everywhere.

```ts
// ❌ Wrong — the same guard duplicated in 3 places today
const lng = i18n.language?.split("-")[0] as SupportedLocale; // language-switcher.tsx
const locale = i18n.language?.split("-")[0] ?? "en";          // use-format-date.ts
const device = getLocales()[0]?.languageCode ?? DEFAULT_LOCALE; // i18n/index.ts
```

```ts
// ✅ Correct — single source (planned `@/i18n/normalize-locale`)
import { SUPPORTED_LOCALES, DEFAULT_LOCALE, type SupportedLocale } from "@repo/i18n";

export function normalizeLocale(raw: string | null | undefined): SupportedLocale {
  const base = raw?.split("-")[0];
  return SUPPORTED_LOCALES.includes(base as SupportedLocale)
    ? (base as SupportedLocale)
    : DEFAULT_LOCALE;
}
```

Callers — `LanguageSwitcher`, `useFormatDate` (`hooks/use-format-date.ts`),
`detectLocale` (`i18n/index.ts`), and the `x-locale` header (§4) — MUST call this
helper. NEVER hand-roll `split("-")[0]` or re-check `SUPPORTED_LOCALES.includes(...)`
inline again. (`SupportedLocale` and `SUPPORTED_LOCALES` derive from `@repo/i18n` —
never redeclare them locally; this is `core/typescript-strict.md` §3.)

---

## 6. Translate all user-facing text — DO NOT translate identifiers

- NEVER hardcode user-facing strings on native — route every label, button, toast,
  and empty/error state through `t(...)`. When you add a key, add it to ALL locale
  files (`en`, `ro`, `ru`) under the same namespace in `@repo/i18n`.
- Use i18next interpolation/plurals (ICU-equivalent), e.g.
  `t("guests", { count: 3 })` against `"{{count}}"` / `_plural` keys.
- DO NOT translate: brand names (DAX), technical identifiers (namespace names, query
  keys, theme tokens, route names), `EXPO_PUBLIC_*` env keys, or storage keys
  (`"dax-access-token"`). These are stable ids, not copy.

```tsx
// ✅ Correct — namespaced, interpolated
const { t } = useTranslation("trips");
return <Text>{t("seats.remaining", { count: free })}</Text>;

// ❌ Wrong — hardcoded copy on native
return <Text>{free} seats left</Text>;
```
